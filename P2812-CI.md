# Automatic P2812HNU-F1 U-Boot builds

The separate [OpenWrt AVM DSL companion](p2812-openwrt/dsl/README.md) reproduces
the verified DSP selection and before-training DSM enable hook. Its own CI
checks the official AVM extraction and OpenWrt overlay; DSP data is not embedded
in U-Boot or published as a repository artifact.

This fork tracks **stable U-Boot release tags**, applies the P2812HNU-F1 port,
builds all boot stages twice, runs the models, compares outputs and publishes
one versioned GitHub Release. RC tags and arbitrary `main` commits are excluded.

The workflow checks upstream every six hours, at minute 17 UTC. GitHub scheduling
is best-effort; **Actions → Run workflow** also performs a check on demand.
If the same upstream commit and port recipe have already been published, it
skips the build. A patch conflict, failed build/test or unequal output stops
publication. The workflow does not attempt to invent a port for incompatible
new upstream APIs.

## Repository layout

- `main`: automation, the reviewed port patch and configuration; keep this as
  the default branch so the scheduled workflow can run.
- `upstream/stable`: the last successfully built official stable commit.
- `p2812/builds/<release-tag>`: immutable generated source for each successful
  build, with the P2812 port applied.
- Releases: firmware, exact source archive, checksums, manifest and test evidence.

The release tag includes the upstream version/commit and a recipe digest.
Changing the reviewed port recipe can therefore publish a new build of the
same upstream version without overwriting an existing published release.

## One-time setup

1. Upload `p2812-ci`, this document and
   `.github/workflows/p2812-upstream.yml` to the fork's **main** branch.
2. Open **Actions** and enable workflows for the fork if GitHub requests it.
   The upload commit may already start the workflow. Otherwise choose
   **P2812 stable upstream build and release → Run workflow → main** once.
3. After the initial successful run, checks and firmware releases run
   automatically. There is **no manual environment release**, image upload,
   registry setup, personal access token or user-provided secret.

The job builds its own Linux/amd64 tools from the repository's two-file
`p2812-ci/builder` recipe. The official Debian base image digest, timestamped
Debian/security snapshots and every installed package version are pinned.
APT verifies signed repository indexes and package hashes; the complete installed
inventory must match `packages.lock` before firmware compilation can begin.
Only expired snapshot freshness dates are disabled, not signature verification.
The job uses its repository-scoped `GITHUB_TOKEN` with `contents: write` for
source branches and releases; no container registry permissions are required.

GitHub disables scheduled workflows in public repositories with 60 days of
inactivity. The monitor makes a small `.p2812-ci-heartbeat` metadata commit on
`main` at most once per 25 days. This is independent of firmware versioning
and does not create a firmware release. The token's own push does not start a
second workflow run.

## Reproducibility and hardware status

The base image and environment recipe, full Debian package inventory, Unicorn
wheel and official OpenWrt test inputs are pinned. The actual built image ID and
verified package inventory are recorded. Every firmware build uses fresh
Linux/amd64 containers with networking disabled and without serial/device mounts.
The firmware source is official upstream plus `p2812-ci/port.patch`.

The previously installed U-Boot v2026.10 baseline is recorded in `config.json`.
For that upstream commit, all firmware hashes must match the hardware-tested
reference. For newer versions the CI tests still run, but a release does not
claim a new physical modem test. This distinction appears in `build-manifest.json`.
The workflow never installs or flashes a modem.

The generated bootloader has the five-second cancellable NAND Linux autoboot
profile, a 16 MiB decode limit and a read-only NAND driver. The release does
not include the separate OpenWrt OS installation, Wi-Fi calibration or user
network configuration. Linux itself can write its normal filesystems.

## Release contents

- `u-boot.bin`, `u-boot.bin.lzo`, `u-boot.uImage`
- `nandfinal1-main-area.img`, `boot-main-256k.bin`, `boot-main-oob.bin`
- `source.tar.gz`: the exact committed patched source used by the build
- `build-manifest.json`, `test-evidence.zip`, `SHA256SUMS`
- `ci-recipe.zip`: environment, controller and port recipe
- `port-diffstat.txt`: changed files/line counts; release notes link directly to
  the official upstream commit → generated P2812 source comparison

Model tests exercise SPL/TPL, ECC/LZO, startup/cache, autoboot and Linux handoff;
they stop before Linux executes. They are not physical DDR/NAND/cache tests or
new-board qualification. A new upstream release may require a reviewed port
update when its API or layout changes; a failing pipeline publishes no firmware.

## Public inputs and privacy

The workflow downloads official public sources and Debian packages and builds
its environment on the GitHub runner. No image built on a Mac is uploaded or
required. The checked-in package inventory contains public package names and
versions. The port contains generic board code, model fixtures, license notices
and test tools, not modem backups, PPPoE/Wi-Fi accounts or calibration EEPROM.
Build manifests record the runner-built container identity and recipe hashes.

Historical vendor source license notices and provenance are retained under
`tools/p2812` in the generated source. The recipe is included in every release
so the build tools can be reconstructed from their pinned public inputs.

## Code review

CI applies a fixed reviewed patch; it does not generate new board-port code.
Every release retains its generated source branch and exact source archive.
The upstream-to-generated-source compare link and `port-diffstat.txt` show what
the port changes, while the previous release's source can be compared separately
to inspect upstream changes. A recipe update is an ordinary reviewable commit
on `main`. Automatic publication does not require a new manual approval gate.
